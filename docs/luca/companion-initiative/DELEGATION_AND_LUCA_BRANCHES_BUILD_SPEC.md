## 1. The experience to build first

The problem is not that Luca lacks an activity dashboard. Asking for a short poem felt like starting a project, watching generic status updates, and waiting several minutes for an answer. The report establishes the experience, not the cause of the delay. The first milestone succeeds when asking another harness feels like asking someone through Luca: **one request, the right executor, one useful answer back in the same chat.**

| When Riley asks… | What the user should experience |
| --- | --- |
| An ordinary question or follow-up | Luca answers in the existing primary conversation. No worker merely to make activity visible. |
| “Ask Claude Code Opus 5.5 to write a poem” | Luca hands the brief to that exact available target. No project picker, checklist, automatic drawer, or repeat approval for unchanged access. If waiting is perceptible, one quiet inline status such as “Asking Claude…”; then the poem, attributed once, with line breaks intact. |
| “Fix this bug” or other substantial work | Luca picks **one** ready connected harness within scope, unless the owner names one. That harness can perform its own multi-step run. One inline task entry, its real plan when available, and a normal way to open or stop it. Luca stays available throughout. Four steps are not four delegation requests. |
| Continue a specific session / just message a native session | Use that exact session/account and saved policy. An app-owned continuation can return a result. Sending to a native-owned inbox confirms *delivery*, not execution or completion; show the supported native link, not a fake Stop or a promise of a reply. |

Use the existing configured primary's identity, not a name match or a new Luca conversation. If both Claude Code and Codex are ready, use Luca's existing turn and its compact capability facts to choose; do not add a model call to route or title each ask. One connected executor **per request**, not one global job: independent owner requests stay independently addressable. Honor named model, project and session; if unavailable, say so once. Do not silently substitute a provider, model, profile, or billing account.

**In scope:** Claude Code and Codex through existing operations; scoped approval reuse; reliable return and task-specific Stop; parent responsiveness; quiet behavior in the existing chat, rail and task detail. Preserve other agents, direct chats, pair inboxes, native harness tools, existing discovery for other harnesses and user settings. **Not in this milestone:** Luca clones (including snapshot-seeded branches), native fork discovery/implementation, parallel coordinator/merge, nested branch sessions, new shared Work/Today UI, inspector redesign, analytics, or new harness integrations. Do not stub them into the user interface.

## 2. Implementation contracts

### 2.1 Dispatch once, within the actual grant

- Bind the host's stable owner, resident, relay/community, originating private home and owner request to the selected harness/account/profile, operation, project (or answer-only scratch), exact native session if any, effective native policy and allowed source/destination audience. Bind requested versus observed model where supported; show unknown evidence honestly. A model-provided ID, a warm process, “Full access,” or a connection alone is not a grant.
- A review may cover more than one already-connected harness only if the owner explicitly selects each scope; it does not launch multiple executors. If the **same access** is already authorized, skip the redundant Polyphonic launch review—not native policy, tool approvals, explicit denies, pauses, sharing limits or provider billing choice. If the owner selects new scope, explain the change once in the existing review; coalesce identical pending reviews. Denial/dismissal does not immediately prompt again. Do not infer observation, retention, model sharing, background initiative or new spending authority.
- Check effective scope at admission, again immediately before dispatch/dequeue, and before releasing private data or returning it. Mint a fresh execution-bound permission lease from the still-valid durable grant. A resident-wide permission-mode change cannot broaden an already admitted task; queued work does not switch accounts or projects when preferences change. Revocation blocks future app-mediated use and requests cancellation of owned running work; it cannot recall data or undo an external effect.
- The root is the owner's request, **not** the lifetime of Luca's initiating turn. Persist a host-issued logical operation ID and immutable request digest before launch. Same ID and digest returns the original authorized receipt; same ID with different data is rejected. A deliberate later identical ask gets its own ID. Do not key solely on prompt text, provider tool-call retries or fresh process IDs.
- Enforce existing task/time/spend limits across app-owned attempts under that root; no unbounded automatic retries and no reset on restart. A changed grant or Stop beats a queued launch. Account for native limits only where enforceable; unknown usage is not zero. Do not impose a blanket two-minute timeout or cut off legitimate long work.
- Use low-side-effect cached readiness and refresh it on relevant changes. For a saved session, revalidate the exact identity, native policy, grant and current binding; if a short-lived lookup expires, refresh just that target when authorized, otherwise report the blocker. Never fall back to “latest.” Neither reading a row nor rendering the shell starts a process or wakes a model.

### 2.2 Return to the right home, once

Keep separate facts: **accepted → launch may have happened → worker outcome → result saved → publication acknowledged**. Reuse the current receipt and encrypted outbox; no competing transcript, signing authority or event bus. The receipt has a logical task ID, attempt, original request/home, executor and result reference. Finishing the provider turn is not proof of correctness, or of delivery to chat.

For a short, complete answer use the existing verified quoted-result path. Preserve the answer and attribution without a second model pass, repeated brief or extra completion message. Never label a truncated result complete. For longer work use the existing result/summary and task detail; show a plan only if the executor actually supplied one. Keep tool arguments, internal statuses and hidden reasoning out of the conversation. One source of truth, not a plan independently authored by Luca to mirror the harness.

Save the result before publication. Address the original owner and primary resident's **exact private two-member conversation**; verify current audience as well as the saved origin at publication/recovery. “Both are still members” is not enough if another participant was added. This private-home rule is specific to this flow; do not change group/inbox delivery elsewhere. If the home is archived, the selected primary changes, or scope cannot be verified, retain the result privately pending permitted delivery; never reroute it to the open chat or create another home.

A busy parent or a newer owner message does not lose or duplicate a result. Return it correlated to the original task without injecting a fake owner message, overwriting the newer turn, or starting a second home writer. A return may acknowledge an older brief; it does not act on that brief again after a correction. A plain answer needs a publication acknowledgement, **not** a further “merge” turn. Tool-capable parent integration is a later branch requirement (§7).

### 2.3 Stop, restart and uncertain delivery

| Evidence held by the host | Required behavior |
| --- | --- |
| Accepted and durably known **never launched** | May resume that same queued intent only if root, grant, target and budget are still valid and no Stop exists. Persist a protected replayable brief/reference when required; a hash alone cannot replay work. |
| Launch reserved or possibly submitted; acknowledgement missing | Reconcile by the exact operation/attempt/native identity. If no authoritative evidence resolves it, mark interrupted/uncertain. Do not retry a command, generate another poem or resend a native message automatically. |
| Worker completed; result saved but not returned | Recover from the durable pending return **by exact task ID**, including outside the latest 512 projections. Never rerun the executor or depend on a rail page or a complete archive scan. Use the exact short answer without model synthesis; for a longer return resume only its still-authorized outstanding delivery step. |
| Return prepared/submitted; relay acknowledgement late or lost | Existing outbox reconciles the same bytes/event. Published means acknowledged; reopening, reconnecting and duplicate callbacks never post a second answer. |
| Task-specific Stop | Persist the root/attempt Stop **before** signalling the owned process. Prevent launch, retry, new publication and late callbacks from reviving that work. Keep unrelated tasks, Luca's newer turn and other residents running. An already-submitted external effect may still arrive: record the race, do not claim it was recalled. |
| External native handoff acknowledged | “Sent to [harness]” settles the *send* for presentation. Execution remains unobserved; keep the exact native link in history. Uncertain delivery gets one actionable issue, not a perpetual running badge. |

Keep existing conversation-Stop semantics distinct from a task-specific Stop. Selecting, closing or minimizing a task view is passive. Do not obtain isolation by stopping Luca's home process. Protect owner/community boundaries during recovery; don't attribute previously unscoped legacy material to whoever is signed in merely to populate a new view.

### 2.4 Existing surfaces only

One visible status/entry per logical task, not simultaneous composer notices, drawer cards and completion banners. A quick ask does not need a persistent card. For longer work, use the approved inline entry and WorkPlan renderer. A normal rail click opens its canonical task in the main surface; label an action that opens the second in-app pane **Open beside**. Nothing opens on dispatch. Preserve drafts, scroll, keyboard focus and the existing composer.

Active rows belong under the executing harness. Keep pending returns and genuine pending decisions reachable; a worker's success alone doesn't settle an undelivered result. Delivered work leaves the active list, not history; keep the selected/pinned/focused item stable during interaction. Dismissals stick to their issue/attempt. Do not hide a specialist that the owner previously revealed. Use existing task links/history for retrieval; no new Today page, Work button or archive-wide UI is needed for this. Preserve typography, glass, marks, Living Ink, motion, zoom and both themes.

## 3. The poem benchmark: start at Send, finish at the poem

Run this when implementation/testing is separately authorized. Use synthetic text in the isolated profile, not Riley's chat history. **Do not send the poem or run a provider test as part of writing this spec.**

- **Owner request, baseline/candidate through Luca:** “Ask Claude Code Opus 5.5 to write a four-line poem about rain tapping on a window. Return only the poem. Writing only; no project files or tools.”
- **Direct control:** in the same native harness and verified model, submit the embedded writing brief directly (“Write a four-line poem …”). Keep account/billing mode, requested and observed model/effort, workspace class, permissions, prompt content and prior task context comparable. Record differences; do not switch to a cheaper model and call it a speedup. Codex also gets a small independent live dispatch/return check with its own available model; it is not the control for Opus.
- **Three paths, two conditions:** record the pre-change candidate, direct native harness and updated candidate, each cold and warm. Cold = first use from an idle test setup with no warm target worker; warm = ready worker with a fresh, equivalent task context, not a cached poem. Do not reset authentication, kill daily-app processes or clear user caches to manufacture conditions. Record actual starting state; if a condition or exact model is unavailable, mark it unmeasured.
- **Primary clock:** from the owner's **Send gesture** to the **complete attributed poem visibly rendered** in the originating chat (complete poem visible in the native control). Also record first meaningful visible response. Record separate correlated times for Luca receiving/routing, any review or queue wait, provider start/first output/finish, result saved, outbox acknowledgement and visible return. Backend “accepted” or “finished” is not the end-to-end metric. Record monotonic elapsed times where available; leave gaps unknown rather than subtracting unrelated clocks.
- **Count the friction:** app launch reviews versus genuinely required native prompts; executor starts; model calls for routing, execution and post-result synthesis; UI interruptions/duplicate messages; available token/cost evidence. Record a short native interaction capture and redacted receipt/trace with actual runtime versions. No prompts, private result bodies, credentials or user identifiers in diagnostics; use synthetic verification/digests for correctness.
- **Pass, established before optimization:** with the matching grant and no native approval required, zero repeat app reviews, one requested executor run, zero auxiliary model calls solely to plan/route/title/paraphrase the poem, zero unsolicited navigation, one unchanged attributed four-line answer, no duplicate publication or edits to project files. Luca's normal turn to interpret the request is not an auxiliary routing call. Preserve the complete provider answer; if the provider itself did not write four lines, distinguish that from a transport or rendering failure. Never silently rewrite or retry to pass. Missing scope or a genuine native confirmation must still be reported honestly; test those separately.
- **Latency decision:** Q0 records individual baseline/control times and freezes an app-overhead regression envelope from repeatable local timings *before* changing the path. Q4 compares matched cold/warm samples, identifies any app-owned wait and measures whether it was removed. Compare provider time separately; native versus Luca wall-time differences alone do not identify the cause. Start with one paired observation per condition; repeat only if authorized and needed to distinguish noise. Use deterministic replay for repeated app-overhead checks. No invented p95 from tiny samples, universal “two-minute” SLA, or performance sign-off on an unmeasured/unexplained regression.

Companion scenarios: (1) While a longer single-harness task runs, send a normal message to Luca; it must be answerable before the worker finishes. Let the task finish and verify the real plan where supplied, stable navigation/focus and one correctly attributed return. (2) In a separate Stop trial, stop one still-running task while another owner request remains active. The stopped task must not start a new publication; the unrelated request can finish normally. Neither trial needs a model call to fabricate a checklist.

## 7. Deferred roadmap — not first-candidate acceptance

### Luca branches: prove one, then two; native fork is optional

1. **One context-seeded branch.** A branch works for the same configured primary, with a distinct logical task, attempt, provider session, Stop and return address—not a new resident, signing key, project, pair inbox or permanent home. Freeze a host-attested committed parent cut, current authorized brief, identity/instructions version, allowable source references, audience, digest and budget. Use the privacy/history compiler and clean-reply attestations. Only include what was available and allowed for that destination at that cut; no secret endpoints, hidden reasoning, unlimited backlog, or fresh sharing grant. Store any private handoff in protected storage. Prove a synthetic fact before the cut is available, a later/revoked fact is not, and Luca can answer the owner while the child works.
2. **Return, then two genuinely independent branches.** Start with one child outliving the initiating turn and returning reliably before adding the second. The [inbox child guard](../../../desktop/src-tauri/src/luca/agent_inbox_child_dispatch.rs) correctly requires an active parent turn for its own flow; do not relax it. Bind a durable root-authorized normal managed continuation for integration, not a fake owner message, a second home writer, or tools in the tool-free result publisher. Record *published* and *incorporated by the parent* separately with deduplicated result IDs. Prove two simultaneous returns, a newer owner correction and a crash between publish/claim/parent commit: integrate once against current authorized context, no stale edit, duplicate response, or spontaneous new root. Stop invalidates the affected continuation; independent work survives.
3. **Bound the entire request and protect the working files.** Proposed initial fan-out limits: two active app-owned child runs per installation, eight queued per root, one level of Luca branching; explicit owner limits win. Concurrent slots are **not** a total budget. Reserve cumulative starts/turns and a shared deadline across batches and retries, bound the global queue fairly, and reserve capacity for the owner to talk to Luca. Respect enforceable spending limits; otherwise disclose unknown native usage. Disjoint paths or isolated worktrees are coordination, not a sandbox. Capture the actual authorized dirty working base (not just Git HEAD), check for overlapping/generated changes and compare before applying. Serialize when isolation cannot be proven; never stash, reset, overwrite local edits, or invent a successful merge. Distinguish branch-reported checks, host-observed tests and accepted changes.
4. **Provider-native fork only when it improves on a seeded child.** Qualify each runtime/version separately. Native resume is not fork. Prove an acknowledged session and committed message/turn cursor, unchanged available parent, permitted history including attachments, fresh child tool bindings and an enforced permission ceiling even if the resident pool mode changes. A native fork must not require closing the live home; use the approved seeded route when those properties are unknown. Cross-provider branches are explicitly seeded and need existing destination/model-sharing authority. Never extract hidden state, join full transcripts or claim two models are identical. Compare the parallel task's quality, total time and cost with one capable harness before making it a default.

If enabled later, only active/selected/pinned working branches nest below Luca. Rail click opens the canonical session in main; **Open beside** opens the existing second pane. Replies go to the selected branch, retaining draft and scroll; viewing never changes execution. Reuse existing marks/uploaded images, task subjects and permission surfaces. A persistent specialist keeps its own inbox and identity. A provider-reported child is inspectable, not automatically messageable or stoppable. One canonical primary rail parent per task; show executor/provenance as metadata, not duplicates. “Merge” means accepted findings, artifacts and reviewed changes—not replacing Luca's history, identity or memory. Existing note consent still governs retention.
